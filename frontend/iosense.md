# IOsense API Tracking — HMEL Steamtrap Reports

Tracks every IOsense function ID used by this app, per project CLAUDE.md rules.

## Auth

| functionID | Used in | Purpose |
|---|---|---|
| `validateSSOToken` | `src/auth/auth.ts` (`exchangeSSOToken`) | Exchanges the one-time `?token=` URL param for a JWT on app load. |

## Devices

| functionID | Used in | Purpose |
|---|---|---|
| `findUserDevices` | `src/services/iosenseApi.ts` (`findDevicesByType`) | Lists all devices with `devTypeName` matching "steam trap", paginated. Response includes `tags[]` per device — this is where department lives, so no extra per-device call is needed. Works with just `Authorization` — no `organisation` header required in practice, confirmed live. **Filters out `IGNORED_DEVICE_IDS`** (currently just `STEAM_GLOBAL_AGG_HEML`, an aggregate/rollup device, not a real individual steam trap — excluded per explicit request 2026-07-16) before returning — since every page and both report generators call this one function, the exclusion applies everywhere automatically. Add more IDs to that `Set` if other non-real devices show up. Confirmed live: device count dropped from 202 to 201 app-wide after the change. |
| `getLastDPsofDevicesAndSensorCalibrated` | `src/services/iosenseApi.ts` (`getLastDataPoints`) | Fetches the latest calibrated `S1` reading (current status) per device in one batch call. |
| `getDataByTimeRangeWithCalibration` | `src/services/iosenseApi.ts` (`getDeviceTimeSeries`) | Fetches raw S1 history for ONE device over a time range. **Response shape gotcha confirmed live (2026-07-16): `data` is an array-of-arrays (`[[{time,value},...]]`), one sub-array per requested pair — NOT a flat array, despite how it reads at a glance.** `getDeviceTimeSeries` unwraps `data[0]`. Superseded for bulk use by `getDeviceAutoDownSampledData` below — kept for single-device use cases. |
| `getDeviceAutoDownSampledData` | `src/services/iosenseApi.ts` (`getBulkDeviceTimeSeries`) | `PUT /account/widget/getAutoDownSampledData` with `devConfig: [{devID, sensor, sTime, eTime, downscale}, ...]` — fetches time series for MANY devices in ONE request. **This is what status-change counting and per-status percentages actually use** (`statusChangeCounts.ts`, `deviceTimeSeriesStats.ts`) — looping `getDeviceTimeSeries` per device (~200 devices) reliably triggered what looked like rate-limiting/CORS blocks on `connector.iosense.io` after repeated use; this bulk call fixed it (confirmed live 2026-07-16, resolves in ~6s instead of failing). **Response shape confirmed live: `data: [{devID, sensor, data: {ISO_timestamp: value, ...}}]`** — note `data[].data` is an object keyed by timestamp, not an array of `{time,value}` objects; `getBulkDeviceTimeSeries` converts and sorts it. `downscale=500` returned 335/336 points for a 7-day S1 range (near-zero data loss vs the raw single-device endpoint) — current default is `downscale=2000` for headroom on longer ranges; revisit if very long ranges (e.g. "Previous 12 Month") start losing real transitions. |
| `trapReplacement/filter` (appserver.iosense.io, not connector.iosense.io — different host, undocumented in the SDK) | `src/services/correctiveActionApi.ts` (`getCorrectiveActions`), `src/services/feedbackApi.ts` (`getFeedbackCountsByDevice`) | Same endpoint, two modes via the `isFeedback` flag: **corrective actions** (`isFeedback:false`) takes a batched `trapDeviceIDs: [...]` array — one call for all devices. **Feedback** (`isFeedback:true`) requires a SINGULAR `devID` instead — confirmed live (2026-07-16) that passing `trapDeviceIDs` with `isFeedback:true` errors `"DevID is required"`; it's one request per device, no batch mode, hence `getFeedbackCountsByDevice` is concurrency-limited (10 in flight) rather than a single bulk call. `PUT /account/trapReplacement/filter/{skip}/{limit}` — paginated (default page size in examples was 10 — always page past it). A "no records" result comes back as `{success:false, errors:["No TrapReplacement found for the user"]}` / `{success:false, errors:["No feedback found for devID <id>"]}`, not an empty array — both handled as zero, not an error. Corrective-action record shape: `{devId, devName, location, manufacturer, trapSize, failure, dateAndTime, correctiveAction, remark, createdAt, ...}` — filter by `dateAndTime` (when the action happened), not `createdAt` (when it was logged). No documented server-side date filter, so corrective actions fetches everything for the given device IDs and filters client-side (cheap — these logs are low-volume). **Feedback response shape gotcha (production bug, fixed 2026-07-16): the successful (non-empty) shape is `{success:true, data:{data:[{feedback, createdAt, ...}]}}` — there is NO `totalCount` field, unlike the corrective-action mode of this same endpoint.** Every device I'd tested before had zero feedback, so I only ever saw the error-shaped empty response and assumed (wrongly) the success shape matched corrective actions' `data.totalCount`. That produced `undefined` for any device with real feedback, and `undefined + number = NaN` when summed for the Daily Report — which corrupted the generated `.xlsx`'s XML badly enough that even `openpyxl` couldn't open it. Fixed by counting `data.data.length` instead. Feedback counts are all-time (not date-filtered) — only `createdAt` exists on a feedback record, no separate event-time field like corrective actions' `dateAndTime`. **No separate device-level "location" text field exists on the device object** — `location` from `getDeviceSpecificMetadata` is lat/long only. There IS a real per-device `Trap Location` **property** though (e.g. `"On OSBL pipe rack PR-12"`) — a much better semantic match for a "Location" column than `devName`; the Daily Report uses it (falls back to `devName` if absent). The Device Detail Report / Management Report still use `devName` for Location (built before this was discovered — not yet retrofitted). |
| `getDeviceSpecificMetadata` (re-added 2026-07-16) | `src/services/iosenseApi.ts` (`getDeviceMetadata`), `src/services/devicePropertiesApi.ts` (`getDevicePropertiesByDevice`) | Was removed earlier this session once tags proved sufficient for department, but properties genuinely have no bulk equivalent — re-added for the Daily Report's Live Status sheet. **`properties[]` holds real, populated per-device fields confirmed live**, not the "undefined, no sensor/formula" the source templates' author notes implied for everything financial: `inletPressure`, `outletPressure`, `baseLineInletTemperature`, `baseLineOutletTemperature`, `Steam Leak` (leak rate, e.g. `"150 Kg/hr"`), `costOfSteam` (numeric), `Trap Location`. **Not real, despite looking like it should be**: sensors `D11` "Steam Loss Value" and `D12` "Steam Saving Value" are defined on the devType but read back as `0` for every device regardless of actual status — confirmed live including on a device in Heavy Leak — so the platform isn't actually computing them in this environment; do not use them for Loss/Saving figures, they'd show misleading fake zeros. `PT1`/`PT2` sensors = live Inlet/Outlet Temperature (°C) — bulk-fetchable via the existing `getLastDataPoints`, no new endpoint needed. Concurrency-limited (10 in flight) — no bulk properties endpoint exists. |

**Department/Unit Name — confirmed against a live token (2026-07-16):** it is NOT a `properties` entry. It's encoded as a tag string in the device's `tags[]` array: `"department:CPP-575"` (colon spacing varies, e.g. `"sec: CPP-575"` has a space, `"department:CPP-575"` doesn't — parsing trims either way). Since `tags` is already returned by `findUserDevices`, no per-device `getDeviceSpecificMetadata` fetch is needed for this — parsed directly via `src/lib/departmentTag.ts` (`extractDepartmentFromTags`). Real sample tags observed: `["<device name>", "type:ST2", "department:CPP-575", "sec: CPP-575"]`.

**S1 status codes — confirmed by client (2026-07-16), source of truth in `src/lib/statusClassification.ts`:**

| Code | Status | Meaning |
|---|---|---|
| 1 | Normal | Discharging condensate correctly, closes against live steam. No action needed. |
| 2 | Mild Flooding | Condensate starting to back up (undersized/partially blocked/failing closed). Early-stage. |
| 3 | Heavy Flooding | Advanced flooding — line substantially waterlogged, kills upstream heat transfer, water-hammer risk. |
| 4 | Mild Leak | Failing open slightly, passing live steam into the condensate line. Small continuous steam loss. |
| 5 | Valve Closed | Isolation valve shut, trap not in service. Not a trap fault. |
| 6 | Choking | Flow obstructed (dirt/scale/stuck mechanism). Tends to escalate — highest priority. |
| 7 | No Status | Algorithm ran but couldn't classify (ambiguous/insufficient signal). Not a health verdict. |
| 9 | Heavy Leak | Failed wide open, continuous live steam loss. Most expensive failure mode. |

Code 8 doesn't exist in the source system. A device with **no S1 last data point at all** is classified as `Offline` (distinct from code 7 `No Status`, which means data existed but was inconclusive) — this is an app-level bucket, not one of the client's codes.

## Pages

- **Steam Trap Status** (`src/pages/SteamTrapStatusPage.tsx`) —
  - **Unit vs Trap Status** matrix: devices grouped by Plant Category → Unit Name (Unit Name = `department:<value>` tag, parsed via `extractDepartmentFromTags`; Plant Category derived from `src/lib/plantCategory.ts`'s lookup, built from the reference management report's Refinery/Petchem sheets — extend it if new department values show up), counted per classified S1 status (`src/lib/statusClassification.ts`).
  - **Corrective Actions & Status Changes** matrix: same Plant Category → Unit Name grouping, with a `DatePicker` (range mode, defaults to current week via `getCurrentWeekRange`) driving two counts per unit — corrective-action records in range (`src/services/correctiveActionApi.ts`) and S1 status transitions in range (`src/services/statusChangeCounts.ts`, one time-series fetch per device, concurrency-limited to 10 in flight via `src/lib/concurrency.ts`, transitions counted by `src/lib/countStatusChanges.ts`).
    - **Date-range gotcha confirmed live (2026-07-16):** the DatePicker's single-day presets ("Today", "Yesterday") resolve to `rangeValue = {start: T00:00:00.000Z, end: T00:00:00.000Z}` — start and end identical, a zero-width window that silently returns 0 for everything. Fixed by always running the picker's output through `normalizeDateRange()` (`src/lib/dateRange.ts`), which expands to full calendar-day boundaries (`00:00:00.000` → `23:59:59.999`) before use. Applied to both the initial default and every `onRangeChange`.
  - **Device Status** table: device name + department + raw current status (S1 sensor) per device.

- **Device Detail Report** (`src/pages/DeviceDetailReportPage.tsx`, second tab in `App.tsx`) — one row per device (all ~200 steam trap devices, no aggregation), with a `DatePicker` (range, defaults to current week) and a Category `SelectInput` filter (Plant Category — All/Refinery/Petchem/Unassigned, options derived dynamically from the data). Columns: Device ID, Location (= `devName`, see gotcha above), Unit (department), Current Status, Duration (selected range in hours, same value every row), all 9 status percentages (`src/lib/statusClassification.ts` `STATUS_COLUMNS` — % of S1 readings in range classified as each status, approximates % of duration assuming roughly-uniform ~30min sampling), Change in Status, No. of Corrective Actions, No. of Feedbacks. Row building in `src/lib/buildDeviceDetailRows.ts`. **Financial columns from the reference report (Leak Rate, Steam Saving/Loss, Cost of Steam, Loss/Savings INR) are intentionally omitted** — the source `.xlsx` templates themselves have unresolved author notes ("Need Sensor and Formula for calculating...") for these, so there's no defined data source yet.

- **Corrective Action Log** (`src/pages/CorrectiveActionLogPage.tsx`, third tab in `App.tsx`) — raw, all-time (no date filter — this is a log, not a period report) list of every corrective-action record for all steam trap devices, newest first. Columns: Name (`devName`), Unit Name (department, joined from the device list by `devId`), Location, Manufacturer, Trap Size, Failure, Corrective Action, Date and Time, Remark — all straight from the `trapReplacement/filter` record (see the endpoint entry above), no aggregation. Row building in `src/lib/buildCorrectiveActionLogRows.ts`. Paginated (25/page) via the same `Table`+`TablePagination` pattern as Device Detail Report.

**Rate limiting — resolved 2026-07-16:** originally used `getDeviceTimeSeries` (one HTTP request per device) for both status-change counting and the detail report's percentages. At ~200 devices this reliably triggered CORS/network failures after repeated use that looked like rate-limiting on `connector.iosense.io` (errors come back without CORS headers, so browsers report a CORS failure rather than the real 4xx/429 — confirmed by testing the exact same request via `curl`, which succeeded, ruling out an actual permissions issue). Fixed by switching to the bulk `getDeviceAutoDownSampledData` endpoint (see above) — one request for all devices instead of ~200.

## Report templates

Registered in `src/reportTemplates/registry.ts`, source formats copied into `src/reportTemplates/files/`:

1. **Steam Trap Management Report** (`management-report-format.xlsx`) — plant/unit rollup, KPIs, corrective action log. **Generation implemented** (see below).
2. **Steam Trap Daily Report** (`daily-report-format.xlsx`) — per-device daily summary + live readings. **Generation implemented** (see below).

Note: both source `.xlsx` templates (copied from repo-root `report templates/`) contain unresolved author notes (e.g. "Need Sensor and Formula for calculating...", "Need condition for defining status") for financial/cost figures — those are omitted from generation rather than fabricated (see below).

### Management Report generation (`src/reportGeneration/`)

Triggered by the "Generate Management Report" button on the Steam Trap Status page (both report buttons now share `components/GenerateExcelReportButton.tsx`, a generic `{idleLabel, generate, filename}` component — the earlier `GenerateReportButton.tsx` was folded into it once the Daily Report needed a second button). Builds a real `.xlsx` (not the HTML-masquerading-as-Excel trick seen in the `reference/hzl-cell-efficiency-db` example app) client-side using `exceljs` (chosen over the free SheetJS `xlsx` build because cell styling — fills, borders, bold — is a paid-tier feature there; `exceljs` is MIT and has full styling support). Orchestrated by `generateManagementReport.ts`, which fetches everything fresh at click time (doesn't reuse whatever the page's date picker currently shows) and always uses the **current week** per spec, then hands off to one builder per sheet:

- `buildOverviewSheet.ts` → `SteamtrapStatusOverview-Refiner` / `SteamtrapStatusOverview-petchem` — report metadata, the KPI table (**Cost of Steam hardcoded to `2473`** per explicit request 2026-07-16 — not derived from device data, same for both reports; Steam Loss, Loss/Savings INR still `N/A` since none have a defined sensor/formula per the template's own author notes; **Overall Trap Health removed per explicit request** even though it had a defined formula), the Unit vs Trap Status matrix filtered to that plant category (**instantaneous** — current status via `getLastDataPoints`/`segregateByUnit`, not time-windowed, per explicit spec), AND a second Plant Category/Unit Name table (Corrective Action count + No. of Status changes, current-week windowed, via `segregateCorrectiveActionsAndChanges`) — **this second table sits ~15 rows below the first in the source template** (rows 22-45 in the Refiner sheet, 27-33 in petchem) and was missed entirely on the first pass because the initial `openpyxl` scan only checked the first ~25 non-empty rows per sheet; caught when the user pointed out it was missing from the generated output. Re-scanning the full sheet (not just the first N rows) found it.
- `buildDetailSheet.ts` → `Refinery` / `Petchem` — reuses `buildDeviceDetailRows` (same as the Device Detail Report tab), filtered by `plantCategory`, current-week windowed.
- `buildCorrectiveActionLogSheet.ts` → `Corrective Action Log` — reuses `buildCorrectiveActionLogRows`, **current-week windowed** (via `getCorrectiveActions(deviceIDs, {startMs, endMs})`) — this was originally all-time but changed per explicit request, since the report itself is generated weekly. (The standalone "Corrective Action Log" *dashboard tab*, `CorrectiveActionLogPage.tsx`, intentionally stays all-time — different use case, a running log rather than a period report — do not conflate the two when making future changes to either.)

All sheets strip the original template's inline help/note text (formula hints, staff names like "Sushant"/"Pavan"/"Taufique" left in cells as reminders) — only real headers + real data. Shared styling (`xlsxStyles.ts`): yellow header fill (`FFFFFF00`, matching the template), bold headers, thin borders on all data cells. Verified live (2026-07-16): downloaded file opens correctly, all 5 sheet names match, row counts match device/record counts exactly, both Plant Category tables present with real current-week data, formatting (fill/bold/borders) confirmed present via `openpyxl`. After the current-week filter was added to the log sheet, verified it correctly shows 0 data rows (header only) since the only known corrective-action records (07/03, 07/09) predate the current week (07/13-07/16) — confirms the filter is actually filtering, not a no-op.

**Lesson for future template scans:** when reading a reference `.xlsx` to replicate its structure, don't truncate the row scan to a small max_row — sheets in these templates have multiple stacked tables separated by blank rows, and a shallow scan will silently miss later ones.

**"Report Generated By"** — the original template had a specific staff name here; omitted from generation since there's no reliable source for "who clicked the button" (only `userId`/`organisation` are available from the SSO exchange, not a display name).

### Daily Report generation (`src/reportGeneration/generateDailyReport.ts` + `buildDaily*Sheet.ts`)

Triggered by the "Generate Daily Report" button, right next to the Management Report one. Unlike the Management Report, this has **NO plant-category segregation** — one flat sheet per concern across all ~200 devices, per explicit spec. Windowed to **today** (`getTodayRange()` in `src/lib/dateRange.ts`, not current week) since it's a daily report, matching its name and the source template's own "Analysis Duration in Hrs: 24".

- `buildDailySummarySheet.ts` → **Summary** — report metadata, an instantaneous status breakdown across all devices (all 9 real statuses, no category split), aggregate counts (feedback/corrective-actions/status-changes, summed across all devices), and Cost of Steam (Rs/Ton) — **hardcoded to `2473`** per explicit request 2026-07-16 (was real, averaged from each device's `costOfSteam` property, until changed — the averaging logic and the `propertiesByDevID` param it used were removed from this sheet builder since they're now dead code). Loss/Savings (MT/INR) stay `N/A` — the D11/D12 sensors that would back these read 0 for every device regardless of real leak status (confirmed live), so using them would show misleading fake zeros, not real data.
- `buildDailyAnalysisSheet.ts` → **Analysis** — one row per device, all together. Reuses the same status-percentage/change-count/corrective-action/feedback-count machinery as the Management Report's detail sheets, PLUS **Leak Rate and (per-device) Cost of Steam are real** here (device properties `Steam Leak` / `costOfSteam`) — a strict improvement over the Management Report's per-device sheets, which still omit these (built earlier, before this properties data was discovered; not yet retrofitted). Note this per-device column is distinct from the Summary sheet's aggregate "Cost of Steam (Rs/Ton)" KPI (hardcoded, see above) — the hardcode request only covered that report-level summary field, not every device row. No separate "Name" column — the source template's short device codes (e.g. "510-HPST-001") don't exist in real data, so Device ID alone is used rather than duplicating it under two headers.
- `buildDailyLiveStatusSheet.ts` → **Live Status** — one row per device: Inlet/Outlet Pressure and Inlet/Outlet Baseline Temperature (real device properties), Live Inlet/Outlet Temperature (real — latest PT1/PT2 sensor readings, fetched in the SAME bulk `getLastDataPoints` call as S1 current status, no extra endpoint). The source template's "Description" column (an auto-generated natural-language explanation of the status, e.g. "Normal means that trap is operating fine...") is dropped — there's no confirmed formula/logic for generating that text, and inventing plausible-sounding explanations would be actively misleading.

**Production bug caught and fixed during first live generation (2026-07-16):** the very first generated file was corrupted — `openpyxl` couldn't even open it (`invalid literal for int(): 'NaN'`). Root cause: `getFeedbackCountsByDevice` (shared with Device Detail Report and the Management Report) assumed the feedback-mode success response had the same `data.totalCount` field as the corrective-action mode. Every device tested up to that point had zero feedback (hit the error-shaped empty response), so this was never actually verified against a real non-empty result. When the full ~200-device run hit one device with real feedback, `totalCount` was `undefined`, and `undefined + number = NaN` when summed for the Daily Report's "Number of feedback" total — corrupting the file's XML badly enough to break even a lenient reader. Found by extracting the raw sheet XML and grepping for the literal string "NaN", tracing it to the exact cell, and testing against a real feedback record fetched live (`{success:true, data:{data:[{feedback, createdAt, ...}]}}` — no `totalCount` at all). Fixed by counting `data.data.length` instead — see the endpoint entry above. **This fix applies retroactively to every consumer of `getFeedbackCountsByDevice`** (Device Detail Report tab, Management Report, Daily Report) since they all share the one function.

Also fixed during verification: live temperature values occasionally displayed floating-point artifacts (`116.21000000000001 °C`) — rounded to 2 decimal places before formatting.

Verified live (2026-07-16) after both fixes: file opens cleanly, all 3 sheet names correct, 202 device rows in Analysis and Live Status (+1 header each), Summary's status counts sum to 202, feedback total correctly shows 1 (matching the one real feedback record found), Cost of Steam averaged correctly from real per-device data, pressure/temperature values match the source properties format exactly (e.g. `"39 kg/cm2"`, `"248 °C"`).
